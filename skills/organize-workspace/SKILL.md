# 工作区组织

先确定工作区根目录、已有项目边界和用户要的结果。已有的项目约定、框架布局和有效入口优先。以下路径是没有既有约定时的建议，不要求为了统一结构搬迁文件，也不建立没有实际内容的目录。

## 按请求选择交付

- 询问归属时，给出建议路径和决定归属的理由。
- 盘点时，只读列出实际路径、用途、仓库边界、有依据的例外和待确认项。
- 规划时，给出目标布局；涉及存量文件时列出需要移动的具体路径。计划与实际变更分开标记。
- 执行整理时，只处理已授权的范围，检查路径引用并验证迁移结果。沿用当前任务已有授权，仅在范围不明或需要扩大操作范围时确认。

## 按维护责任决定位置

| 内容 | 默认位置与判断依据 |
| --- | --- |
| 独立版本化的项目 | 新建多仓工作区可用 `app/<项目名>/` 承载具体 Git 仓库。源码、测试、依赖、构建脚本和 CI 跟随各自项目。单仓和 monorepo 沿用已有布局。纯运维工作区不必设置 `app/`。 |
| 一次任务的过程和证据 | 需要长期追溯时放 `tasks/YYYY-MM/YYYY-MM-DD-主题/`，日期按工作区约定的时区。创建前查找同主题记录；跨会话续做沿用同一任务，一次跨仓交付共用一份记录，可链接多个 PR 或提交。不按每次对话或小改动新建任务。已有 Issue/PR 足以追溯的单仓小改可直接引用。 |
| 长期配置 | 工作区统一维护的配置放 `config/`；随项目发布的配置和模板留在项目仓库。环境特有值在目标环境维护，模板使用占位值。 |
| 脚本与工具 | 单次采集脚本随任务，项目专用脚本随项目。已有重复用途、由工作区维护时才提取可复用版本到 `tools/`。在当前索引或新增路径映射中记录新入口，保留历史脚本与证据原文。 |
| 公共模型与运行资源 | 先检查已有公共资源清单，核对适用系统、运行环境和访问路径后复用。共享文件不代表环境可跨机器运行；公共目录不可访问时说明情况，不默认重复下载或部署。可重建依赖与缓存按目标运行环境管理，不默认随资料迁入共享存储。 |
| 导航、规范与手册 | 根 `README.md` 指向项目、当前入口、任务索引和少量重要记录，按下节控制索引规模。`AGENTS.md` 写工作区约定与例外。持续更新的跨项目手册按需放 `docs/`。同一份正式源码、配置或手册维护一处，其余位置使用链接。 |
| 历史资料 | 已退役的工具和方案可整体放 `archive/YYYY-MM/主题/`，注明退役原因和替代入口。完成的任务仍留在 `tasks/`，保留原始报告、日志和校验清单。历史路径已变化时另写映射。归档不等于删除，不因文件较旧就删除。 |
| 敏感内容与临时产物 | 私钥、令牌、原始认证信息和完整敏感配置使用受限存储。任务记录只留脱敏结论及允许披露的引用。聊天数据库等本机应用状态不随项目资料迁入共享存储。按复核需要保存原始证据，其余临时输出使用临时目录；本地留存与 Git 收录分别判断。 |

任务 README 保持为简短摘要与导航，记录目标、日期、涉及项目、实际结果、验证范围与未决项。有部署或迁移时补充生效入口与回退位置；有 Issue、PR 或关联会话时附引用。详细过程、分阶段记录和日志保存在同一任务目录的独立文件中，按需链接。已有长 README 可先搜索相关段落，不为缩短上下文删除或改写历史证据。

## 控制索引与读取范围

- 根 `README.md` 保持为简短导航，链接任务总索引及少量当前重要任务，不持续追加全量任务清单。已有短索引可保留，不为层级本身拆分。
- 没有既有索引约定时，任务少可在 `tasks/README.md` 平铺；难以快速定位时再按月份或主题分组。总索引以分组入口为主，具体任务放到对应分组；任一层过长时继续拆分，避免只是把根目录的长清单搬到另一处。
- 每条只保留日期、主题、必要的状态和链接，不粘贴完整结论、日志或文件清单。一个任务维护一个主条目，其他入口引用它；后续进展更新当前导航或追加带日期的说明，历史结论与原始证据保留原文。
- 新任务更新所属索引，仅在需要改变主要导航时更新根 `README.md`。从根索引撤下任务前，确认仍可经分组索引或已有检索入口找到；撤下入口不代表移动、归档或删除任务文件。调整后按链接所在文件的位置验证相对路径。
- 读取时先确认直接适用的工作区与项目约定，再按主题、日期或路径搜索定位，逐层读取相关索引、任务 README 和确有需要的证据片段。不默认展开所有链接、读取全部任务正文或扫描整份日志；长索引也可先搜索相关条目。全量目录盘点可以列出元数据，不等于需要读取所有文件内容；需要全量内容核查时以用户要求和实际验证范围为准。
- 索引随维护责任和可见范围放置：跨仓、本机运维记录放管理工作区；公开仓库文档只收录适合公开维护的入口，不带入本机绝对路径、私有任务内容或内部会话链接。

## 整理现有工作区

1. 识别普通目录、独立仓库、submodule、worktree 和符号链接。目录名只提供线索，必要时用 `git rev-parse --show-toplevel`、`git worktree list` 或 `git submodule status` 核对归属。保留现有仓库边界、分支、Stash、未提交改动、未跟踪及被忽略的本地资产；不擅自修改符号链接指向的范围外内容。
2. 为拟移动项列出原路径、目标路径、归属理由和受影响的引用。重点查服务启动、计划任务、CI、脚本与文档入口；若存在多个副本，先确认哪份实际被使用。归属不明的项保留原位并说明缺少什么证据。仍被运行入口引用、且未获入口变更授权的路径也保留原位。
3. 在授权范围内迁移，保留可逆的路径映射，不覆盖已有目标。跨卷或跨存储迁移先复制，完成与数据重要性相称的内容和必要元数据校验后，再按已有授权切换入口及处理源文件；不能只凭目标目录存在判断成功。失败或中断时停止受影响的批次，保留源文件与已复制内容并记录未完成范围。移动已登记的 worktree 或 submodule 时使用其现有 Git 管理方式。合并仓库、删除副本、提交或推送、改服务配置、重装、重启或变更计划任务不由目录整理自动授权。
4. 验收原有文件和本地改动是否完整、仓库是否仍可识别、受影响的入口和链接是否有效、运行状态是否符合原有状态或本次明确授权的变更。报告已移动项、验证结果与待确认项，并同步当前索引。

## 示例

`example-api` 和 `example-web` 是两个虚构项目。若该工作区已采用 `app/` 布局，一次 API 字段调整同时涉及两者时，各自在 `app/example-api/` 和 `app/example-web/` 修改代码与测试。若还包含联调上线，在 `tasks/YYYY-MM/YYYY-MM-DD-接口联调上线/` 建一份记录，链接两个仓库的提交并写下实际验证结果。

若为这次联调编写了临时检查脚本，先随任务保存。之后若多个项目都要定期运行它，再将可复用版本放入 `tools/`，在当前索引或新增说明中链接原任务和新入口，保留当时的验证结果。
